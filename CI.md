# Сборки в CI

Два воркфлоу в `.github/workflows/`:

| Файл | Когда | Что делает |
| --- | --- | --- |
| `ci.yml` | push в `main`, любой PR | `flutter analyze --no-fatal-infos` + `flutter test` |
| `release.yml` | тег `v*` или запуск руками | Android AAB + APK → Google Play (закрытое тестирование), iOS IPA → TestFlight |

Репозиторий публичный, поэтому раннеры GitHub Actions — включая macOS для iOS — бесплатны без лимита минут.

## Как выпустить релиз

```bash
git tag v1.0.3 && git push --tags
```

Либо вкладка **Actions → Release → Run workflow**. При ручном запуске галка «Заливать в сторы» по умолчанию снята — соберутся только артефакты, в магазины ничего не уедет. Полезно, чтобы проверить пайплайн, не тревожа тестировщиков.

**Версию задаёт тег**: `v1.0.3` → в сборке будет `1.0.3`. То есть поднять версию — это назвать тег, править `pubspec.yaml` для этого не нужно. Инкрементировать версию сама CI не может и не должна: из кода не видно, патч это или минор. Ручной запуск без тега берёт версию из `pubspec.yaml`.

**Номер сборки** считает CI: `BUILD_NUMBER_OFFSET` (100) + номер прогона воркфлоу. Обоим сторам важно только то, что каждый следующий номер строго больше предыдущего; отступ 100 взят с запасом над теми `+7`, что заливались руками. Если когда-нибудь придётся заливать билд в обход CI — поднимите отступ в `release.yml`, чтобы нумерация не столкнулась.

## Секреты

Добавляются в **Settings → Secrets and variables → Actions → New repository secret**.

| Секрет | Откуда | Без него |
| --- | --- | --- |
| `ANDROID_KEYSTORE_BASE64` | `base64 -i upload-keystore.jks \| pbcopy` | сборка уходит с debug-подписью: Play её не примет и поверх установленного приложения она не встанет |
| `ANDROID_STORE_PASSWORD` | из `key.properties` | то же |
| `ANDROID_KEY_PASSWORD` | из `key.properties` | то же |
| `PLAY_SERVICE_ACCOUNT_JSON` | Play Console → Setup → API access → сервисный аккаунт с правом Release to testing tracks, скачать JSON целиком | AAB остаётся артефактом прогона, в Play не уезжает |
| `APP_STORE_CONNECT_KEY_ID` | App Store Connect → Users and Access → Integrations → App Store Connect API | iOS соберётся без подписи — только проверка, что проект компилируется |
| `APP_STORE_CONNECT_ISSUER_ID` | там же, над таблицей ключей | то же |
| `APP_STORE_CONNECT_PRIVATE_KEY` | `.p8` скачивается **один раз** при создании ключа: `base64 -i AuthKey_XXXX.p8 \| pbcopy` | то же |

Отдельно — **переменные**, а не секреты (та же страница, вкладка **Variables**):

- `PLAY_TRACK` — трек Google Play, по умолчанию `alpha`. Названия в API и в консоли не совпадают: `internal` = Внутреннее тестирование, **`alpha` = Закрытое**, `beta` = Открытое, `production` = прод. У именованного закрытого трека идентификатор свой — его и указывать.
- `ANDROID_KEY_ALIAS` — алиас ключа в keystore, по умолчанию `upload`. Алиас — это имя, а не тайна, зато секретом GitHub маскирует его по всему логу: алиас `upload` превращал строку `actions/upload-artifact` в `actions/***-artifact`.
- `ANDROID_CERT_SHA256` — отпечаток сертификата, которым релиз обязан быть подписан. После сборки CI спрашивает у APK, чем он подписан, и падает при расхождении. Смысл в том, что debug-подписанный релиз внешне неотличим от нормального — узнаёшь об этом уже от Play. Не задана — CI просто печатает отпечаток и предупреждает; этим значением её и заполняют после первой сборки.

Пайплайн написан так, что недостающие секреты его не ломают: шаг проверяет, что задано, пишет warning в лог и пропускает то, что без ключа сделать нельзя. Можно включать по частям.

## Что нужно получить у владельца Apple-аккаунта

Команда `3PR335XF64` принадлежит не вам, поэтому ключ App Store Connect должен выпустить её владелец. Просить лучше **не `.p12` с сертификатом**, а одно из двух:

1. **Ключ App Store Connect API** с ролью App Manager — три значения из таблицы выше. Это и подпись, и загрузка в TestFlight, и он не протухает через год, в отличие от сертификата.
2. Либо **приглашение вас в команду ролью Admin** — тогда такой ключ вы выпускаете себе сами и больше ни от кого не зависите.

## Подводные камни

- **Первый релиз в Play-трек заливается руками.** Play API умеет обновлять приложение, но не создавать его и не открывать трек.
- **Лимит Distribution-сертификатов.** `-allowProvisioningUpdates` выпускает сертификат прямо на раннере, а раннер каждый раз чистый — значит каждый релиз тратит слот, а их у команды всего три. Когда упрётся: отозвать лишние в Developer Portal, а по-хорошему — перейти на `fastlane match`, который хранит один сертификат в отдельном приватном репозитории.
- **`xcrun altool`** Apple давно называет устаревшим. Если однажды он исчезнет из Xcode на раннере, шаг загрузки в TestFlight меняется на `xcrun iTMSTransporter` или на готовый action — остальной пайплайн не трогается.
- **Канал Flutter.** CI собирает на `stable`, локальная разработка идёт на `master`. Если stable окажется старше того, что нужно коду, — в `FLUTTER_CHANNEL` (обоих воркфлоу) пишется конкретная версия.
- **Репозиторий публичный.** GitHub не отдаёт секреты воркфлоу из форк-PR и маскирует их в логах, но всё, что шаг напечатает сам, видно всем. Не добавляйте `set -x` в шаги, где есть ключи.
